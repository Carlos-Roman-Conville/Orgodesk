# Issues

Known limits, things found while building, and what has not been verified. Numbers are never reused.

| # | Status | What |
|---|---|---|
| FC-1 | fixed 2026-11-06 | `SHChangeNotifyRegister` with more than one entry in a single call raises an access violation inside shell32 on this machine (Windows 11 26200, .NET 8), even with a blittable entry struct. Single-entry calls work. The watcher now registers one call per folder. |
| FC-2 | fixed 2026-11-06 | Shell APIs were called before COM was initialized on the UI thread (the watcher was built in a constructor, before any WinForms window). `Application.OleRequired()` now runs at startup and the watcher is created after the surface attaches. |
| FC-3 | resolved 2026-11-06 | Stardock Fences was installed on this PC and its hook `FencesMenu64.dll` sat inside explorer.exe during the build, so both programs fought over the icon list. Rex has since uninstalled it: `Fences.exe` is gone and no uninstall entry remains. Leftovers only: a dead `HKCU\...\Run\Fences` value pointing at the missing exe, and a few DLLs in `C:\Program Files (x86)\Stardock\Fences`. Neither can run. |
| FC-4 | fixed 2026-11-06 | The desktop's own show/hide toggle (`WM_COMMAND 0x7402`) flips the `HideIcons` registry value and Explorer took 5 to 10 s to apply it, so the first start logged "Could not hide the real desktop icons" and the watchdog finished the job later. The app now shows/hides the `SysListView32` window directly with `ShowWindow`: instant, nothing persisted, so a crash cannot leave the desktop empty after a reboot. The toggle is only a fallback. The watchdog re-hides the list within 2 s if Explorer shows it again. |
| FC-5 | open | The desktop's shell background menu still offers **View > Show desktop icons**. Picking it flips Explorer's own setting; the watchdog hides the list again within 2 s, but the registry value is then out of step with what is on screen until it is toggled back. Filtering that item out of the shell menu is not done. |
| FC-6 | open | Icons are loaded synchronously on the UI thread the first time they are drawn. A shortcut to an unreachable network target can stall the first paint for a few seconds. A background loader with placeholders is the fix. |
| FC-7 | verified | Verified by Rex by hand on 2026-11-06: right-drag fence creation, fence move and resize (with snapping), roll-up, auto-roll, shell context menus, dragging icons into and out of a fence, lasso select, quick hide, desktop pages. Still untried: drops onto a portal, drops from an Explorer window, inline rename. |
| FC-8 | not verified | DPI change, resolution change and multi-monitor layouts. The surface re-sizes on `SystemEvents.DisplaySettingsChanged`, clamps fences into the new virtual screen, and scales sizes per monitor through `GetDpiForMonitor`, but this PC has one 1920x1080 monitor at 100%. |
| FC-9 | not verified | Keyboard input across processes. The surface is a child of Explorer's DefView, so it attaches its thread input to Explorer's desktop thread and calls `SetFocus` on click. If keys do not arrive, that attachment is the place to look. |
| FC-10 | open | Renaming a non-filesystem item (for example a special folder) goes through `IShellFolder::SetNameOf` and was not tested. Filesystem renames use `SHFileOperation` and keep hidden extensions. |
| FC-11 | fixed 2026-11-06 | Free icons could sit under a fence (seen with a hand-seeded layout). Fences never leaves icons under a fence: after a fence is created, moved, resized or unrolled, free icons under it are now moved to the next free grid slot. |
| FC-12 | open | The wallpaper is not captured by `PrintWindow` on the desktop, so screenshots taken that way show black behind the surface. On screen the wallpaper shows through normally (the surface clears to alpha 1 of 255). |
| FC-13 | open | Not implemented from Fences: "exclude this fence from quick-hide", roll animations, icon size per fence, fence transparency per fence. Auto-roll (peek) and fence snapping were added on 2026-11-06 at Rex's request. |
| FC-14 | note | When probing from PowerShell, pass `[NullString]::Value` (not `$null`) as the title to `FindWindow`/`FindWindowEx`; `$null` marshals as an empty string and matches nothing. During the build that returned one of the Stardock Fences hook's hidden list views instead of the desktop list, and a `ShowWindow` on it put a white "wall of blank icons" on Rex's screen until it was hidden again. `Orgodesk.exe --diag` prints what the app itself sees. |
| FC-15 | note | With the Stardock Fences hook loaded, explorer.exe keeps about twenty hidden top-level `SysListView32` windows (one per Fences fence, widths 222 to 1920, height 1100). They are Fences' machinery, not Explorer's desktop list, and the clone never touches them. Restarting Explorer after exiting Fences clears them. |
| FC-16 | fixed 2026-11-06 | Crash (`ObjectDisposedException: ContextMenuStrip`) on the first click after a fence or create-fence menu closed: the strip was disposed inside its own `Closed` event and WinForms' modal menu filter still touched it on the next activation change. Disposal is now deferred with `BeginInvoke`. Found by Rex in the first hand test; the crash handler restored the real desktop icons as designed. |
| FC-17 | fixed 2026-11-06 | Right-click showed the real desktop menu next to the clone's own menu: an unhandled `WM_CONTEXTMENU` bubbles from a child window to its parent (`SHELLDLL_DefView`). The surface now swallows it. Found by Rex in the hand test. |
| FC-18 | fixed 2026-11-06 | ISSUES.md rows FC-5 to FC-13 were lost by a careless "replace from FC-14 to end of file" edit after FC-14 had been inserted mid-table. Restored from the build notes; edit this table row by row. |
| FC-19 | fixed 2026-11-06 | Double right-click toggle (switch the clone off and on) did nothing at first: the second click lands on the menu the first click opened (a classic popup on the clone, a XAML popup on the Windows 11 desktop), so a window check rejected it. After a right-click on the desktop, a quick second right-click at the same spot now counts whatever is under it. Verified by Rex. |
| FC-20 | fixed 2026-11-06 | Switching presets always applied the first one: saving cloned the active page and kept the page's id, so every preset shared one id. New presets now get their own id, duplicates already saved are repaired on load, and a test covers two presets switching. Found by Rex. |
| FC-21 | note 2026-11-06 | Renamed from Fences Clone to Orgodesk (folder, projects, namespaces, exe, install dir, Run value, shortcut, data folder). `--install` stops the old copy (legacy exit event), removes its Run value, shortcut and install dir, and `%APPDATA%\fences-clone` is moved to `%APPDATA%\orgodesk` at startup. The old copy still writes its layout to the old path as it exits, leaving an identical duplicate folder behind; removed by hand once. |
| FC-22 | fixed 2026-11-07 | Orgodesk did not start after two restarts. Cause: it was installed from Claude's sandboxed shell, and registry writes from that sandbox never reach the real registry, so the Run value existed only inside the sandbox and Windows never launched Orgodesk at login (Win32_StartupCommand and StdRegProv did not list it). A first fix wrongly assumed an early launch and added a 120 s wait for the desktop; that wait was removed. Kept: start, exit and desktop-not-found lines in error.log. Fix: run `--install` outside the sandbox (or by Rex), then confirm the Run value through StdRegProv, not through the shell. |
| FC-23 | open 2026-11-07 | Claude's sandboxed shell also keeps its own copy of %APPDATA% (Roaming) and %LOCALAPPDATA% root files: the layout, presets and settings it wrote never reached the real `%APPDATA%\orgodesk`, so the Orgodesk Rex installed started with a near-empty layout. Desktop, E: and `%LOCALAPPDATA%\Programs` are real. `restore\finish-setup.bat` (run by Rex) copies layout, settings and snapshots into the real folder. From now on, edit layouts through Orgodesk itself or hand Rex a .bat. |
| FC-24 | note 2026-11-08 | Windows Controlled Folder Access blocks Orgodesk.exe from writing `%userprofile%\Favorites` each time an icon is opened through Orgodesk (Defender event 1123). The launch still works; the shell is updating a recent list. Harmless; Rex can allow Orgodesk in Ransomware protection if the alert bothers him. Also: to change the real layout from a sandboxed agent, run `restore\export-layout.bat` and `restore\import-layout.bat` through Orgodesk or File Explorer (see FC-23). |
| FC-25 | fixed 2026-11-11 | Found in the VM test (fresh Windows 11 Home build 26300): Orgodesk showed about 15 items Windows' own desktop hides (Home, Gallery, Libraries, Control Panel, OneDrive, the user folder, Desktop/Documents/Downloads/Music/Pictures/Videos, both CD drives). Cause: enumerating the desktop root also returns navigation-pane items, and none of them carry SFGAO_NONENUMERATED (checked), so no attribute filter works. Rex's PC (build 26200) returns Home, Gallery, Libraries, Control Panel and Linux the same way; he keeps them on purpose in his Places Orgo. Fix: `ExplorerDesktopView` reads Explorer's own desktop view (IShellWindows.FindWindowSW SWC_DESKTOP, then IShellBrowser, IFolderView.Items), and `EnumerateDesktop` keeps an item only if Explorer shows it, it is a file in the user or public Desktop folder, it is a known desktop icon, or it is already placed in an Orgo or on the desktop in any page or preset (so Places keeps working). If the view can't be read, nothing is dropped. VM check: fresh install shows only Recycle Bin, Edge and Learn about this picture; Home placed in an Orgo stays. Screenshots `G:\VMs\orgodesk-test\shotsix-*.png`. |
| FC-26 | fixed 2026-11-11 | Found in the VM test: deleting `%APPDATA%\orgodesk` (or losing settings.json any way) silently turned off start-with-Windows. At every start `TrayContext.Start` makes the Run value match `Settings.StartWithWindows`, and that setting defaulted to false, so a fresh settings.json removed the Run value `--install` wrote; the VM then did not start Orgodesk after a restart. Fix: `StartWithWindows` defaults to true (an explicit false is still saved and kept: the serializer writes every value). Tests: missing settings file keeps it on; saved false stays false. VM check: Run value still present after the data folder was deleted, and Orgodesk started by itself after the next restart (17:01:29). |
